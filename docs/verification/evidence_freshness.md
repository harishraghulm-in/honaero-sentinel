# HonAero Sentinel — Cryptographic Evidence & Freshness Lifecycle

Verification records must be immutable and audit-proof. Any subsequent modification to the target source code, stub mock behaviors, or test vector specifications automatically invalidates previous verification evidence.

---

## 1. Cryptographic Checksum Composition

All SHA-256 hashes generated by Sentinel are canonicalized:
- **Canonical JSON**: Object keys are sorted alphabetically recursively, and compact JSON is hashed.
- **Timestamps Excluded**: Timestamp fields are explicitly excluded from cryptographic content hashes so that identical source code and configurations yield identical SHA-256 digests across different execution runs.

---

## 2. Freshness States

| State | Definition | Trigger Condition |
| :--- | :--- | :--- |
| **`CURRENT`** | Valid and up to date | Source code SHA-256, stub SHA-256, and vector SHA-256 match the sealed Evidence Record. |
| **`STALE`** | Out of date | Target source code, stubs, test vectors, or compiler flags have been modified since verification execution. |
| **`INVALIDATED`**| Unusable | Underlying source files or test suites have been deleted or corrupted. |

---

## 3. Automated Invalidation Tracking

When an Evidence Record becomes `STALE`, Sentinel identifies the exact affected test cases (`affected_test_cases: ["TC-1", "TC-2", ...]`) and reports an explicit diagnostic explanation:
```json
{
  "freshness": "STALE",
  "source_changed": true,
  "reason": "Source changed after verification. (Original: 9d81dbd7..., Current: 3dc89fec...)",
  "affected_test_cases": ["TC-1", "TC-2", "TC-3", "TC-4"]
}
```
Re-execution is required to transition the evidence state back to `CURRENT`.
